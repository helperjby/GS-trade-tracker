# 사통팔달 `0x1f82` — 프로토콜 판정과 가설 레지스트리

사통팔달(서버 전체 외치기) 수집 트랙의 **분석 정본**이다(2026-10-14). 형식은 `docs/PACKET-MARKET.md` 와 같다 — 게이트
사다리·등급 정의는 SEAssist `docs/PACKET-PROCESS.md` §1~§3 동결 시점(main b54cb73) 참조. 실플레이어 이름·글·실기기명·창
파일명은 옮기지 않는다(공개 레포 규칙, `AGENTS.md`).

## 1. 결론

- 사통팔달은 서버 8000 s2c **opcode `0x1f82`** 한 종류로 온다. 프레임은 **75B 고정**(길이 접두 2B 포함, 본문 73B).
  접속해 있는 클라는 **아무것도 하지 않아도** 받는다(idle 베이스라인 6종에 원래 들어 있던 번호다). 4011 채팅 연결이 아니다.
- 본문 = 보낸이(cp949 20B, NUL 종료) + 1B + 내용(cp949 40B, 짧으면 NUL 종료·꽉 차면 NUL 없음) + 꼬리 7B. NUL 뒤는 서버 버퍼
  잔재다(값이 매번 다르다) — 첫 NUL 까지만 읽는다.
- **서버 식별자는 프레임에 없다.** 어느 서버의 사통인지는 수집하는 사람이 정한다(관측기 `--satong <서버 번호>`).
- 서버는 사통을 **약 15초 간격**으로 한 건씩 내보낸다(큐). 같은 PC 의 클라가 여럿이면 같은 외치기가 클라마다 한 번씩
  온다(도착 차이 수 ms).
- 등급 **B(유력, 구조 + 외부 대조)** — 2026-10-14. 관측 전용 배선(파서·업로드)에 넣을 수 있다.

## 2. 표본

| 구분 | 수치 |
|---|---|
| 창 | 119창(기기 폴더 5개, 2026-07~10) 중 사통 프레임이 있는 창 44 |
| 프레임 | **고유 252**(같은 흐름의 TCP 재전송 사본 제외 — 원시 바이트 검색은 사본까지 334를 센다) |
| 재생 | `FlowDecoder(observe_satong=True)` + `parse_satong` 으로 119창 재생: 수용 252 · 거부 0 · 유실 0 · 파싱 실패 0 · anomaly 0 |
| cp949 해독 실패 | 0 |

창 파일(원시 캡처)은 레포 밖에 둔다 — 파일명에 기기명이 들어가고 본문에 다른 플레이어의 글이 있다.

## 4. 외부 대조 (G5, 2026-10-13)

외부 공개 사통 기록(서버 단위 게시 사이트, 2026-10-06 부터 접근 차단돼 미루봇 원본 교체의 계기가 됐다)의 같은 서버 기록과 대조했다.

- **같은 시간 창별 건수**: 패킷 42 · 외부 기록 45. 가장 붐빈 창은 11 vs 11. 차이는 창 경계의 시각 반올림 몫이고, 패킷에만 있는
  글이 없다 → 다른 종류의 외치기가 섞이지 않는다.
- **길이**: 외부 기록의 본문 최대 40B — 패킷 내용 필드 폭과 같다.
- **보낸이**: 패킷 보낸이 90명 중 18명이 외부 기록 스냅샷 세 개에 그대로 있다 → 수집 클라의 서버와 기록의 서버가 같다.
- **지문 직접 대조**: 0건 — 외부 기록의 시각이 마이크로초 단위라 원래 재구성이 안 된다(반증 아님).

## 6. 수집 경로

관측기 `--satong <서버 번호>`(운영자 PC 전용, 기본 꺼짐) → `satong_observer` 가 클라 간 중복(같은 보낸이·내용 10초)을 걸러
`POST /api/satong/observations` → 허브 `satong_messages` → 미루봇 `GET /api/satong/recent`. 계약은 `docs/HUB-PROTOCOL.md` §3-8.

## 7. PATCH-RECHECK

헬스 줄의 흐름별 `1f82=` 가 0 으로 남고(접속 중인데) `srej=` 가 오르면 본문 드리프트, 둘 다 0 이면 번호 이동 의심이다.
`--capture 5` 창을 한 번 남기고(사통이 몇 건 지나가게) `0x1f82` 자리에 새로 생긴 75B 근처 번호를 찾는다. 바뀌면 `SATONG_OPCODES` 에
추가하고 이 문서 §5 에 행을 더한다.
