# 육의전 목록 응답 `0x321f` — 프로토콜 판정과 가설 레지스트리

이 트랙(육의전)의 **분석 정본**이다. 2026-09-21 Step 1 분석은 SEAssist 레포에서 했고(동결 시점 문서
`docs/PACKET-MARKET-2026-09-21.md` · `PACKET-PROCESS.md` §3), 2026-09-22 방향 전환으로 **후속 기록은 여기**
(`docs/PLAN.md` §1). 이 문서는 그 분석을 이 레포로 옮긴 판이다 — 실판매자명·실기기명·창 파일명은 옮기지 않는다
(공개 레포 규칙, `AGENTS.md`).

재현:

```
python tools\market_probe.py --root <패킷 루트>                     # 라이브 재생 vs 프로브 대조 + 라벨 대조
python tools\market_probe.py --root <패킷 루트> --window 2023 --rows
python tools\dump_item_names.py --ids 853,3506                     # 아이템 id → 이름
```

수집은 관측기 `run_dev.bat --capture 5`, 콘솔 라벨 `market_manual`(README "수집 절차").

## 1. 결론

- 육의전 목록은 서버 8000 s2c **opcode `0x321f`** 한 종류로 내려온다. 본문 = **9B 헤더 + 48B × 행 수**
  (한 페이지 최대 10행). 열기·검색·초기화·페이지 넘김마다 프레임 1개이고, 관측 40/40 프레임이
  `len(body) == 9 + 48×count` 를 만족한다. 이 등식이 판별의 핵심이다(`gersang_protocol.is_market`).
- 행의 **수량(`@8` u32)·가격(`@16` u32)·판매자(`@24` cp949)** 는 콘솔 라벨 8행과 **8/8** 일치한다.
- **아이템명은 어느 프레임에도 없다.** 아이템은 `@4` u32 **id** 로만 온다 → 이름은 클라 리소스 표에서
  관측기가 붙인다(H-2609-10, `src/yuktracker/item_names.py`).
- **페이지 번호는 응답에 없다**(요청에만). 헤더 `[3]`·`[4]` 는 페이지 1~10 프레임 10개 전부 0 이고,
  페이지는 등록 id 가 ~10씩 내려가는 것으로만 이어진다 → 소비자는 등록 id 로 페이지를 잇는다.
- 등급 **B(유력, 구조)** — 2026-09-21 확정. A 로 가려면 용병(Lv) 탭 행, 수량 ≥65,536 경계, PC 세션 추가.

## 2. 표본

| 구분 | 수치 |
|---|---|
| 양성 창 | 9창 / 5세션 / 3 PC(2026-09-14·16·21), 전체 검토 폴더 80창 중 |
| 음성 창(목록 UI 를 열지만 육의전이 아닌 것) | 2창 — 전서구, 상단·상단 상점·전장 |
| 음성(기존 사냥 창 코퍼스) | 73창 `0x321f` 0건 |
| 프레임 | 40(고정 코퍼스 등록분 39 + 미등록 1창 1) · 행 369 |
| 라벨 앵커 | 8행 8/8 일치 |

창 파일(원시 캡처)은 레포 밖에 둔다 — 파일명에 기기명이 들어가고 본문에 다른 플레이어의 판매자명이 있다.

## 3. 프레임 판정 (G1~G3)

- `0x321f` 의 sub-id(=`body[5:9]` u32) 다봉은 **(총 페이지 u16, 행 수 u16)** 으로 전부 설명된다.
  길이 분포 [9, 57, 249, 297, 345, 489] = `9 + 48 × {0, 1, 5, 6, 7, 10}`.
- 자극 창 밖 출현은 매크로 세션 2창뿐이고, 둘 다 사용자가 그때 육의전을 열었다고 확인했다(양성).
- 같은 목록을 두 번 열면 헤더·행 배치가 같고 내용만 그 사이 등록분만큼 밀린다.
- 육의전 창을 여는 순간 1페이지가 오고, `물품구매` 버튼과 창 닫기는 s2c 를 만들지 않는다.
  열기 직후 `0x2fc7`(41B)·`0x3056`(41B)이 동반한다(의미 미상, D).

## 4. 필드 표

offset 은 body 기준. 행 k 의 필드는 `9 + 48k + 상대 offset`. 캡처 2026-09-14~21 · s2c · 8000 · 클라 09-14 패치 이후.

| offset | size | type/endian | name | semantics | 등급 | 근거 | falsifier |
|---|---|---|---|---|---|---|---|
| 0 | 1 | u8 | magic | `0x00` | A(프레이머) | 30/30 | ≠0 |
| 1 | 2 | u16 LE | opcode | `0x321f` | C | 30 프레임 · 8창 · 2 PC · 09-14~21 | 육의전 외 UI 에서 출현 / 클라 패치 후 소멸 |
| 3 | 1 | u8 | reserved | 0 | C | 30/30 | ≠0 |
| 4 | 1 | u8 | 미상(항상 0) | **페이지 번호가 아니다** — 페이지 넘김 9프레임 전부 0 | C | 30/30 | ≠0 이면 의미 재조사 |
| 5 | 2 | u16 LE | total_pages | 총 페이지 수: 기본 목록 218~247(요일·시각에 따라), 검색 11행 2 · 6행/5행/1행 1 · 0행 0 | C | 30/30 | 행 수 ≤10 인 단일 응답인데 ≥2, 또는 count>0 인데 0 |
| 7 | 2 | u16 LE | count | 이 프레임의 행 수 0~10 | C | 30/30 `len == 9 + 48×count` | 불일치 프레임 1 |
| +0 | 4 | u32 LE | listing_id | 등록 id — 시간 순 증가(≈1,850/일). 기본 목록은 **내림차순(최신 우선)**, 페이지 넘김은 10씩 내려간다 | C | 269행 · 21프레임 내림차순 | 같은 id 가 다른 아이템·판매자로 재등장 |
| +4 | 4 | u32 LE | item_id | 아이템 id(라벨 8종 확인: 853·2,204·3,506·5,317·6,215·6,342·8,245·13,468) | C | 라벨 8행 + 같은 아이템 묶음(3506×7행 · 853×11행) | 같은 아이템 두 행의 id 상이 |
| +8 | 4 | u32 LE | quantity | 판매 개수. 관측 1~1,218 | C | 라벨 **8/8** | 라벨 불일치 1행 |
| +12 | 4 | — | 0 | 항상 0 — quantity 상위 4B(u64) 또는 패딩 | C | 269/269 | 비영 → u64 확정 |
| +16 | 4 | u32 LE | price | 단가. 관측 50,000~160,000,000 (≥65,536 다수 → u16 불가) | C | 라벨 **8/8** | 라벨 불일치 1행 |
| +20 | 4 | — | 0 | 항상 0 — price 상위 4B(u64) 또는 패딩 | C | 269/269 | 비영 → u64 확정 |
| +24 | 16 | cp949 NUL 종료 | seller | 판매자명(관측 ≤10B). **NUL 뒤 잔여 바이트가 213/269 행** — 서버 버퍼 잔재라 첫 NUL 까지만 읽는다 | C | 라벨 8/8 | 16B 초과 이름 / NUL 없음 |
| +40 | 4 | ? | 미상 | **프레임 내 전 행 동일.** 검색 응답은 작은 값(0x28·0x30·0x58), 기본 목록은 큰 값(프레임마다 다름) | D | 269행 | — |
| +44 | 1 | u8 | 0 | 항상 0 | C | 269/269 | ≠0 |
| +45 | 1 | u8 | 미상 | 1(67행) 또는 2(202행) — UI `기간` 후보(H-2609-11) | D | 269행 | — |
| +46 | 1 | u8 | 미상 | 0~7 | D | 269행 | — |
| +47 | 1 | u8 | 0 | 항상 0 | C | 269/269 | ≠0 |

D 등급 필드는 **이름을 붙이지 않는다** — 파서는 `unknown40`·`flag45`·`flag46`·`raw44`·`raw47` 로 원값을 그대로 낸다.
"항상 0" 관찰은 판별 조건이 아니라 `anomalies` 다(꼬리 상수 일반화로 기각된 선례 H-2607-05).

## 5. 라벨 대조 (앵커 8/8)

콘솔 라벨은 화면 첫 행의 `아이템, 수량, 판매자, 단가` 를 사람이 옮겨 적은 것이다. **판매자 칸은 합성 이름으로
바꿔 적는다**(실제 값은 레포에 남기지 않는다 — 대조의 근거는 수량·단가가 맞았다는 사실이다).

## 8. 인게임 `물품 목록` 창 열 ↔ 필드

창은 `아이템`/`용병` 탭이고 열은 `물품명 · 레벨 · 판매개수 · 판매자 · 구매개수 · 단가 · 총가격 · 기간`.

| UI 열 | 필드 | 비고 |
|---|---|---|
| 물품명 | `@4` item_id → 표 | H-2609-10 |
| 레벨 | — | 아이템 탭에선 전부 0 — **용병 탭 전용**(미수집) |
| 판매개수 | `@8` quantity | 라벨 8/8 |
| 판매자 | `@24` seller | 라벨 8/8 |
| 구매개수 · 총가격 | — | UI 입력·파생값(패킷 없음) |
| 단가 | `@16` price | 라벨 8/8 |
| 기간(장기/단기) | `@45` 후보 | H-2609-11(D) |

소비자(미루봇 `!육의전 <아이템>`)에 필요한 정보 4종 = 물품명·판매개수·판매자·단가. 수집 시각은 패킷이 아니라 관측기 벽시계(`agent_ts`)다.

**소멸 규칙(게임 사실, 패킷 아님 — 사용자 확인 2026-09-23)**: 등록일 D(KST)에 올린 물품은 팔리지 않으면 단기 = D+2 00:00, 장기 = D+3 00:00
에 사라진다. 등록 시각·페이지 번호가 응답에 없으므로 허브는 관측 시각(`first/last_seen_ts`)에서 소멸 경계를 추정한다(HUB-PROTOCOL §4).
`기간`(`@45`) 이 D 등급이라 **검정 전엔 모든 행을 단기로** 본다 — §11 ① 의 라벨 5열 캡처가 곧 만료 계산의 정확도로 이어진다.

## 10. PATCH-RECHECK — 클라 패치로 번호가 옮겨 갔을 때

전례가 있다(조철 `0x30dd` → `0x30df`). 관측기 헬스의 **`market_frames` 가 계속 0 인데 사용자는 육의전을 열었다**면:

1. `--capture 5` 로 육의전 열기·검색·페이지 넘김을 라벨과 함께 새로 수집한다(README 절차).
2. `python tools\market_probe.py --root <패킷 루트>` — 페이지 0(rc 2)이면 번호가 옮겨 간 것이다.
3. 새 창에서 `len(body) == 9 + 48×count` 를 만족하는 s2c 프레임의 opcode 를 찾는다(헤더 패턴 검색은
   `market_probe.probe_frames` 의 `HDR` 상수를 바꿔 가며).
4. 찾은 번호를 **관측된 것만** `gersang_protocol.MARKET_OPCODES` 에 더한다(산술 오프셋 추정 금지 —
   캡차는 −8, 조철은 +2 로 움직였다). 이 문서의 §7 에 관측 근거와 날짜를 남긴다.
5. `market_rejected` 가 올라가는데 프레임은 온다면 번호가 아니라 **본문 배치**가 바뀐 것이다 — §4 를 다시 검정한다.
